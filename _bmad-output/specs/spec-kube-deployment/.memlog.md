- (direction) Spec covers the KUBE assignment infrastructure/deployment project only; the Laravel app's own code is frozen and out of scope per user direction
- (capability) CAP-1 intent: operator can stand up a fresh, reproducible Kubernetes cluster across the 3 provided AWS nodes with a single Ansible run; success: running the playbooks against a torn-down environment yields a working cluster with no manual steps
- (capability) CAP-2 intent: users can reach every exposed app and tool securely over HTTPS through a single ingress layer; success: every exposed hostname resolves via sslip.io/nip.io and serves a valid TLS cert with no plaintext HTTP
- (capability) CAP-3 intent: operator can view and manage cluster workloads through a web dashboard instead of raw kubectl; success: dashboard shows live pod/deployment state and accepts basic management actions, reachable only after OIDC login
- (capability) CAP-4 intent: operator can observe system and application health through collected metrics and receive alerts on problems; success: a dashboard shows live metrics for cluster and app, and a deliberately broken condition fires a visible alert
- (capability) CAP-5 intent: operator can search and visualize centralized logs from every workload; success: a log query in the logging UI surfaces recent log lines from the app and from cluster components
- (capability) CAP-6 intent: operator can manage every reusable infrastructure component (ingress, dashboard, monitoring, logging, IdP, etc.) declaratively from Git, auto-reconciled into the cluster; success: a change committed to the infra GitOps repo is applied to the cluster without manual kubectl commands, and the operator UI shows it in sync
- (capability) CAP-7 intent: the sample Laravel app, originally run via docker-compose, can be deployed to the cluster as a Helm chart with its database deployed via the database's official chart; success: helm install/upgrade of the app chart produces a running app connected to a running database
- (capability) CAP-8 intent: operator can deploy and update the application declaratively from its own GitOps repo, separate from the infra repo, with sync and health verified automatically; success: a commit to the app GitOps repo triggers an automated deploy and the operator reports the app as synced and healthy
- (capability) CAP-9 intent: anyone accessing a deployed tool (Grafana, dashboard, GitOps operator UI, kubectl) or the Kubernetes API must authenticate via OIDC against a self-hosted identity provider; success: an unauthenticated request to any covered tool or to the k8s API is redirected to login, and a valid login grants access
- (capability) CAP-10 intent: the cluster rejects requests that violate baseline policy (e.g. missing resource limits, missing mandatory labels, disallowed image registry) via a native admission policy; success: a deliberately non-compliant manifest is rejected at apply time with a policy violation message
- (capability) CAP-11 intent: the database's data survives pod restarts; success: deleting and recreating the DB pod leaves previously written data intact, backed by the shared EFS-backed PersistentVolume
- (capability) CAP-12 intent: a scheduled job automatically performs a real operational task on a recurring basis; success: the CronJob runs on schedule and its output (e.g. a backup artifact or report) is verifiable afterward
- (capability) CAP-13 intent: deploying a new app version never interrupts service, and a broken new version never receives live traffic; success: during a rollout with a deliberately failing readiness probe, the app stays reachable throughout and only the previous healthy version serves requests
- (capability) CAP-14 intent: application images are published to and pulled from a private, authenticated registry rather than a public one; success: the cluster pulls the app image using registry credentials, and the registry is not publicly readable
- (constraint) Cluster must be provisioned and deployed with Ansible so it can be torn down and rebuilt reproducibly (imposed, non-negotiable)
- (constraint) Admission control must use native ValidatingAdmissionPolicy (CEL-based), not a third-party policy engine (imposed)
- (constraint) Authentication must use OIDC via dex, covering every deployed tool (Grafana, dashboard/Headlamp, GitOps operator, kubectl) plus the Kubernetes API itself, against a self-deployed identity provider such as Keycloak - no external corporate directory is available (imposed)
- (constraint) All exposed endpoints must be served over HTTPS via cert-manager and Let's Encrypt (imposed)
- (constraint) Application images must be published to and pulled from a private authenticated registry (imposed)
- (constraint) Infra and application deployment must live in two separate GitOps repositories, kept cleanly separated
- (constraint) Only 3 AWS nodes are available: kube-1 (control plane plus worker, stable public IP that survives nightly shutdown, the entry point for DNS/TLS) and kube-2/kube-3 (workers, unstable public IP, stable private VPC IP) - architecture and access patterns must respect this topology
- (constraint) No load balancer or wildcard DNS is provided - ingress exposure must go through NodePort resolved via sslip.io or nip.io
- (constraint) All VMs auto-shutdown nightly and must be manually restarted - demo and implementation sessions must plan around this
- (constraint) No plaintext secret may be committed to Git - sensitive data must go through Sealed Secrets or External Secrets into Kubernetes Secrets, all other configuration into ConfigMaps
- (constraint) Every resource must carry Kubernetes-recommended labels
- (constraint) Application containers need multiple replicas with anti-affinity so replicas of a service land on different nodes
- (constraint) Database persistent storage must use a PersistentVolume backed by the group's shared Amazon EFS filesystem; surviving a full cluster deletion is not required
- (constraint) Every workload must define CPU and RAM requests and limits
- (constraint) VM access is via AWS SSM Session Manager using school-email IAM Identity Center login, not VPN or public SSH; own SSH keys may be layered on top afterward
- (direction) Non-goal: no changes to the Laravel application's own code, routes, migrations or business logic - it is a fixed given, per user direction
- (direction) Non-goal: surviving a full cluster teardown is not required for persistent data, only surviving pod restarts
- (direction) Non-goal: integrating an external/corporate identity directory is out of scope - the IdP is self-hosted inside the cluster
- (direction) Non-goal: the bonus items (kube-rbac-proxy multi-tenancy, Helm artefact security evaluation, fine-grained RBAC, network policy hardening, lightweight images, documented cluster upgrade process) are optional stretch goals, not required for the core deliverable
- (decision) Success signal: a live defense demo where Ansible provisions a fresh cluster, a new app version is deployed via a GitOps commit (not manual setup), the rollout keeps the app available and a deliberately faulty version never receives traffic, and OIDC, HTTPS and the admission policy are visibly enforced
